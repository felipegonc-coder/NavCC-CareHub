# 0003: Docker image and single-server deploy

- **Status:** proposed (2026-10-26; revised 2026-10-27 for #10 and #15, for the deploy plan (build on the server, tailnet only), then for the security review: the app's own database role, the LAN firewall rule, `TRUST_PROXY`, least privilege; then `npm ci` with no `npm install` fallback)
- **Context:** Care Hub runs on one small server, reachable only over Tailscale. It needs HTTPS (a `*.ts.net` name), PostgreSQL, uploaded files, backups that are known to restore, and updates that happen only when a person decides. CI has to stay within 2,000 free minutes a month (0006). No credentials of the shared GitHub account may end up on the server, and nothing should be exposed that doesn't have to be (#10, #15).

## Decision

1. **The server builds its own image.** It clones the repository with a read-only deploy key, checks out a version that passed CI on `main`, and `deploy/up.sh` runs `docker compose up --build`. No registry login, nothing is published: CI has no `packages: write`.
2. **One image** (`Dockerfile`): the server bundle with its production dependencies, the built web app, migrations, `LICENSE` and `THIRD_PARTY_NOTICES.md`, on port 3000, with a health check on `/api/health`. Dependencies come exactly from the lockfile with `npm ci --ignore-scripts` (0011), with no `npm install` fallback: if the lockfile is out of sync with a `package.json`, the build stops. `up.sh` passes `CAREHUB_VERSION` (`git describe`) and `CAREHUB_BUILD_DATE` for the Status page.
3. **`image.yml` runs only on request:** by hand and on pull requests labelled `image`. It checks the deploy rules below in `docker-compose.yml` and the `Dockerfile`, builds the image and tests the deploy as a server runs it: `install.sh`, `up.sh`, HTTPS through Caddy, a backup asked for like the Status page does, and `restore.sh`.
4. **Data in `CAREHUB_DATA_DIR`** (default `/srv/carehub`): `postgres/`, `files/`, `backups/` and `caddy/` as bind mounts, owned by one service user (`carehub`), mode 700. The secrets are in `deploy/.env` (root only, mode 600), which `install.sh` creates.
5. **Tailnet only:** Caddy publishes ports 80 and 443 only on the server's Tailscale address and gets the `*.ts.net` certificate from tailscaled. `carehub-firewall.service` adds a `DOCKER-USER` rule that drops traffic to that address unless it comes in on `tailscale0`, since Docker's published ports bypass ufw and Linux accepts such packets on any interface. The app and PostgreSQL publish no ports. The firewall denies all inbound traffic; SSH only over Tailscale. The Tailscale policy tags the server `tag:carehub`, lets people reach only ports 80 and 443 and admins also 22, has no rule with the tag as source, and Funnel and Serve stay off.
6. **Containers** run as the service user, never root, with `no-new-privileges`, no capabilities (Caddy keeps `NET_BIND_SERVICE` in its bounding set only so that its binary starts) and without the Docker socket. The app and Caddy have read-only root file systems. Two networks: `front` (Caddy, app) and `back` (app, PostgreSQL, backups; internal), so Caddy can't reach PostgreSQL. Caddy has a fixed address on `front`, passed to the app as `TRUST_PROXY`, so the app sees each person's address. Base images (`node`, `postgres`, `caddy`) are pinned by digest and bumped by hand in a pull request.
7. **Database roles:** the app connects as its own role (`carehub`), which owns the database but isn't a superuser and can't create databases or roles. `db-init.sql` creates it when PostgreSQL sets up its data folder. The superuser is only for backups and restores; restores run as the app's role (`--no-owner --role`), so it still owns everything. The app gets only the settings it needs, never the superuser's password. PostgreSQL uses `scram-sha-256` for every connection, never `trust`.
8. **Updates and rollbacks are manual:** `up.sh` builds while the old version runs, backs up, starts the new version (the app runs its migrations at start) and checks its health. A rollback checks out the previous version and runs `up.sh`, or `restore.sh` with the backup from before the update when the database changed.
9. **Backups:** `pg_dump` and a tar of the files daily, before each update and on request, kept 30 days. A backup counts only after it was restored into a scratch database and the archive was read back. The app sees only the results (`backups/status/`), never the backup files. One backup runs at a time, a request less than 60 minutes after the last run is ignored, and a backup doesn't start with less free space than twice the last one.

## Consequences

- A merged change reaches the server only when a person checks it out and runs `up.sh`. Building takes a few minutes and some disk space on the server; old images and build cache are removed by hand.
- Node, PostgreSQL and Caddy fixes arrive only when someone bumps the digests.
- `image.yml` costs runner minutes only when someone asks for a run.
- The deploy needs a few host steps that scripts only check: the service user, `TS_PERMIT_CERT_UID`, `net.ipv4.ip_nonlocal_bind = 1` (so Docker can bind the Tailscale address at boot), the firewall, `carehub-firewall.service` and the Tailscale policy.
- A new app setting reaches the app only once it's added to the app's `environment` list in `docker-compose.yml`.
- `db-init.sql` runs only on an empty data folder: changing the roles of an existing database is a manual step.
- Backups sit on the same server, unencrypted, until someone copies them off encrypted (age or gpg, by hand). Automating that comes later.
