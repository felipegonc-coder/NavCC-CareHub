# 0200: Databases and forms storage and API

Status: accepted (Databases and Forms lead), Oct 27, 2026. Builds on 0007 (shared contracts). Shapes are the ones in `packages/databases/src/types.ts`; request bodies are checked with `@carehub/databases/schemas`; views are answered with `@carehub/databases/engine`.

## Storage (Postgres, Drizzle, migrations `NNNN_databases_*.sql` and `NNNN_forms_*.sql`)

Databases and rows are pages (0007): a database is a page of kind `database` (inline or not), each row a page of kind `row` whose parent is the database page. Titles, icons, covers, content, trash and sharing live on the page. Our tables hold the rest. A template's page is a page of kind `row` under the database with no `db_rows` entry: everything that lists rows reads `db_rows`, so templates never show as rows, and their search text is empty.

| Table             | Key                  | Columns                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `db_databases`    | `page_id` (pages.id) | `workspace_id`, `properties` jsonb (Property[]), `views` jsonb (View[]), `templates` jsonb (RowTemplate[]), `access_rules` jsonb (RowAccessRule[]), `default_template_id`, `locked`, `row_page_layout` jsonb, `sub_items` jsonb, `dependencies` jsonb, `deleted_properties` jsonb ({ property, deletedAt, values }[] for 30-day restore), `next_unique_number` int, `version` int, `created_at`, `updated_at` |
| `db_rows`         | `page_id` (pages.id) | `database_id`, `workspace_id`, `values` jsonb (property id → stored value), `unique_number` int, `created_by` (null for anonymous responses), `created_at`, `edited_by`, `edited_at`, `form_view_id` (null unless made by a form), `import_id` (null unless imported)                                                                                                                                         |
| `db_row_changes`  | id                   | `row_id`, `database_id`, `at`, `by` (null: anonymous), `property_id`, `before` jsonb, `after` jsonb (row history; 90 days)                                                                                                                                                                                                                                                                                    |
| `db_imports`      | id                   | `database_id`, `by`, `upload_id`, `status`, `row_count`, `problems` jsonb, `created_at`, `undone_at`                                                                                                                                                                                                                                                                                                          |
| `db_import_files` | `import_id`          | `bytes` bytea (the uploaded file until the import job ends; deleted then)                                                                                                                                                                                                                                                                                                                                     |
| `db_exports`      | id                   | `database_id`, `by`, `file_name`, `csv` text, `row_count`, `created_at` (kept 24 hours)                                                                                                                                                                                                                                                                                                                       |
| `db_button_runs`  | id                   | `database_id`, `row_id`, `property_id`, `by`, `at`, `outcome`, `changes` jsonb (for Undo and the run log; newest 50 per button)                                                                                                                                                                                                                                                                               |
| `db_repeat_state` | `template_id`        | `database_id`, `next_run_at`, `last_run_at`, `paused_reason`                                                                                                                                                                                                                                                                                                                                                  |
| `db_reminders`    | id                   | `row_id`, `property_id`, `fire_at`, `sent_at`                                                                                                                                                                                                                                                                                                                                                                 |

Indexes: `db_rows (database_id)`, `db_rows (database_id, unique_number)`, GIN on `db_rows.values` (reverse relation lookups), `db_rows (form_view_id, created_by)` (one response per person), `db_reminders (fire_at) where sent_at is null`.

Writes to a database's settings take `select … for update` on its `db_databases` row and bump `version`; clients send `version` and get `409 conflict` ("This database changed. Reload to see the latest.") when it moved. Every settings write (`PATCH /:id`, properties, views, view order, templates and access rules) sends `version` and answers with the whole database as `GET /:id` returns it, with its new `version`; a property type change also returns `cleared` (how many values were cleared). Row writes never lock the database row.

## Who can do what

Page access comes from the pages API (`getPageAccess`, `getAccessForPages`, `requirePageAccess`). Rows inherit the database's level; `edit_content` becomes `edit` on rows; `rows_only` gives `view` on the database page and `none` on rows until a row access rule lifts them (our `registerAccessResolver('row', ctx)`). Property access (`Property.access`) is applied on every response: hidden properties and the formulas and rollups that read them are stripped, and a view that uses one answers only `{ blocked: "This view uses a property you can't see." }` (issue #46). Forms aren't blocked this way: a form shows only its own questions. Page mentions in rich text: wherever the server sends rich text (values, row pages, search results, notices), it checks page access and leaves out the title of any mentioned page the viewer can't open.

| Action                                                                                    | Needs                                                                                 |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Read database, query views, open rows                                                     | view (rows: their row level)                                                          |
| Comment on rows                                                                           | comment                                                                               |
| Add, edit, delete, reorder rows; use templates; press buttons that change rows            | edit_content (rows only via rules: their row level; adding rows needs "Can add rows") |
| Properties, views for everyone, options, templates, lock, sub-items, dependencies, import | edit, Lock structure off                                                              |
| Row access rules, property access, form audience, anonymous, closing                      | full                                                                                  |

Form routes are the default export of `apps/server/src/features/forms/routes.ts` at `/api/forms`:

| Route                                               | Does                                                                                                                                                       |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /:code`                                        | The fill screen's form (questions, gate state, anonymous line) for a signed-in member or guest                                                             |
| `POST /:code/responses`                             | `{ answers }` → `{ ok: true }`; checks with the form logic, writes only mapped questions that were shown                                                   |
| `POST /:databaseId/views/:vid/link`                 | "Change link": revokes the old code                                                                                                                        |
| `GET /public/:code`, `POST /public/:code/responses` | Forms anyone on the network can fill in (FM-D2, off by default per form): `config: { public: true }`, 30 responses a minute per form, the conditions below |

Security reviewer's conditions (OK given Oct 27):

- Forms anyone can fill in: link codes from `crypto.randomBytes(16)` as base64url, kept out of the Caddy and Fastify logs; each response checked against the form definition (show-if included) and only mapped, shown questions written (#46); atomic `closeAt` and `maxResponses` checks; batched notices; no CORS headers, and #29's CSRF double-submit still applies; a signed-in person arriving on the public route is ignored, so the response stays anonymous. Optional: a signed timestamp from the GET for a minimum fill time.
- Anonymous uploads (files scope `forms:<formId>`, `registerFileScope` with `allowAnonymous: true`, our `canWrite` decides): each upload tied to the response being filled in, which attaches only its own uploads; unattached files deleted after about an hour; a daily byte quota per form plus a free-disk floor; office files only as docx, xlsx and pptx (no docm, xlsm, pptm or old binary formats; content must match the extension); always served as a download, PDFs included; pictures re-encoded; clean file names (path separators, control characters, U+202E) and an RFC 5987 Content-Disposition; per-IP limits rely on `trustProxy` set to Caddy only.

## Events, live updates and other lanes

- Events through `app.events` after commit, IDs and small facts only (`events.ts` exports the names, payload types and `onDatabaseEvent(handler)`): `databases.row.created { workspaceId, databaseId, rowId, actorId, source: 'user' | 'import' | 'form' | 'automation' | 'button' | 'template', formId?, responseId? }` (`actorId` null for anonymous form answers), `databases.row.updated { workspaceId, databaseId, rowId, actorId, propertyIds, source }` (one per row; `propertyIds` are the properties whose values changed, plus the Name property's id on a rename), `databases.row.trashed` and `databases.row.restored { workspaceId, databaseId, rowIds, actorId }`, `databases.database.viewed { workspaceId, databaseId, viewId, userId }` (a view's first page), `databases.database.updated { workspaceId, databaseId, actorId, what }` (settings). Team tools' automations and analytics listen to these.
- Live: `publishTopic('db:<databaseId>', { type: 'rows-changed', data: { rowIds } })` after commit (no row ids when the database has row rules), and `{ type: 'schema-changed' }` for settings.
- `apps/server/src/features/databases/api.ts`, server functions for other lanes; each checks access first and refuses (403) before any change: `listDatedRows`, `listDateSources`, `setRowDate` (Team tools calendar layers, signatures from that lane), `listViewRows`, `createRow(tx, { databaseId, templateId?, values?, actorUserId, source, formId?, responseId? }) → { rowId }` (`actorUserId` null only with source `'form'`, for anonymous answers), `createRows(tx, { databaseId, rows, actorUserId, source, importId? }) → { rowIds }` (`importId` sets `db_rows.import_id`), `updateRows(tx, { databaseId, rowIds, values, actorUserId, source }) → { rowIds }`, `readRow(db, { userId, rowId })` (the values that person may see; Person values as user ids), `readRowText(db, { userId, rowId, propertyIds })`, `createDatabase(tx, definition)`, `duplicateDatabase(tx, { databaseId, parentId, includeRows, by })`, `exportViewCsv(db, { userId, databaseId, viewId })`. Row writes run inside `runRowWrites(app, async (tx) => …)`: it opens the transaction, commits, then sends the events, live updates and notices, and `createRow`, `createRows` and `updateRows` throw on a `tx` from anywhere else. Each call runs in its own savepoint, so a refused call (`HttpError` 400, 403 or 404) leaves the caller's transaction usable. And `registerRowAccessLimiter(kind, limiter)` for other features' rules on rows (the Knowledge base's `'wiki'`: Draft articles only for their owners and editors): `limiter({ databaseId, row: { id, values, createdBy }, properties, userId, level }) → AccessLevel`, synchronous and without I/O, may only lower `level` (anything higher is ignored). The row resolver applies it to databases with that flag, so views, counts, search, links, mentions, backlinks, notices and direct requests (403) all follow it.
- Share links: `registerShareLinkGuard('database' | 'row', isShareLinkSafe)` refuses databases with row access rules or property access.
- Move to: handle `page.kindChanged` (a row that becomes a page loses its values; a page that becomes a row starts empty).
- Search: `registerSearchText('row', …)` with visible text only.
- Jobs: CSV import and export, repeating templates (every 15 minutes), date reminders (every minute).

## Web

Database pages render through `pageKindViews.database`, rows through the page view with `pageHeaderExtras.row`, inline databases through the editor's `nodeViews.database` (`packages/editor/src/lanes/databases.ts`), forms at `/forms/:code`. Every colour, font, size and spacing comes from the design kit tokens; no one-off styles.

Test hooks (for our tests and the Testing lane's flows; roles and names first, a few ids where they aren't enough):

- Database page or inline block: `data-testid="database"` with `data-database-id`. View tabs: role `tab` named after the view.
- Table: role `grid`; headers role `columnheader` named after the property; rows role `row` with `data-row-id`; cells role `gridcell` with `data-property-id`. Totals row: `data-testid="db-totals"`.
- Board columns `data-testid="board-column"` with `data-group-key`; cards role `article` with `data-row-id`. Calendar days `data-testid="calendar-day"` with `data-date` (YYYY-MM-DD). Timeline bars `data-testid="timeline-bar"` with `data-row-id`. Chart: role `img` named after the view.
- Buttons by their text ("New", "Filter", "Sort"). The row page (side peek or center) is a role `dialog` named after the row's title; full page is the page route.
- Form fill: role `form` named after the form's title; each question labelled by its text; submit by its label; the confirmation is role `status`.
- In a test: `POST /api/databases { parentId, inline: false, title }`, then `POST /:id/properties`, `POST /:id/views` (`layout: 'form'` for a form) and `POST /:id/rows`. The form's link code is `view.form.linkCode` in `GET /api/databases/:id` (people who can edit); the fill screen is `/forms/<linkCode>`.
